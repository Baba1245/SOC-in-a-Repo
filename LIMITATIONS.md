# Limitations

This project is deliberately honest about what it does *not* do. Detection
engineering portfolios usually fail by overclaiming; the point of this document
is to state the boundaries plainly so the numbers can be trusted.

## Sigma compilation is a documented subset

The compiler translates a **subset** of Sigma into Wazuh PCRE2 rules and
**refuses everything else** rather than mis-translating it.

* **Supported:** field modifiers `endswith` / `startswith` / `contains` / `all`;
  value lists (OR) and `|all` (AND); conditions `selection`, a single-key
  selection, `all of sel*`, `all of them`.
* **Not supported (skipped and reported):** `1 of selection_*` and other
  cardinality conditions, `re`/regex modifiers, `|base64`/`|base64offset`,
  numeric comparisons, `timeframe`/correlation, `null` checks, and nested
  boolean expressions with parentheses.

Skipped rules are surfaced in the compile report and **do not count toward
attempted coverage**. `detections/sigma/proc_creation_win_powershell_encoded_UNSUPPORTED.yml`
is committed on purpose to exercise and test this path. A rule you cannot compile
is not coverage, and the matrix says so.

## Validation is modelled in CI, real in the lab

`socrepo validate` (simulated) computes `validated` by running the compiled PCRE2
field patterns against pinned process-creation telemetry in memory. This is a
faithful-enough model of Wazuh's process-creation field matching (AND across
`<field>` tags, case-insensitive PCRE2) so the loop is reproducible without a live
endpoint — but it is a model:

* It covers **process-creation (Sysmon EventID 1)** only. Techniques that need
  network, registry, image-load, or file telemetry are out of scope for the
  simulated validator (and for the scoped Sysmon config in `config/sysmon/`).
* It does not model Wazuh decoding quirks, rule ordering/`if_sid` chains beyond
  the Sysmon parent (`61603`), aggregation, or FTS. The **same compiled rules**
  deploy to the real Wazuh manager in `infra/`, where full-pipeline behaviour is
  authoritative.
* "Validated" therefore means "a representative atomic's telemetry makes the
  compiled rule fire," not "validated under production load with real EDR noise."

## Atomic GUID pinning (reproducibility, not live coverage)

Each technique in `data/mappings/attack_scope.yaml` pins explicit Atomic Red Team
`guid`s, and the validation telemetry is keyed by the same `auto_guid`. This makes
"validated" refer to a *specific* atomic rather than a moving target.

The trade-off: pinned GUIDs can drift from the upstream Atomics repo over time.
When you bump the Atomics version you must review and update the GUIDs
deliberately — the pin is a reproducibility guarantee, not a claim that these are
forever the current atomics. Simulated validation also proves the *detection*
matches representative telemetry; it does not prove the *atomic still executes* on
a modern, patched Windows build. Confirm that in the live lab.

## Sample corpus is synthetic (but provenance-documented)

`data/sample_alerts/alerts.jsonl` and `data/labels/manual_labels.csv` are
generated by the committed, deterministic `scripts/build_sample_corpus.py`. They
are realistic and include deliberate context-flip edge cases, but they are
**synthetic**: not sampled from a real SOC, not IID with any real alert
distribution, and modest in size (~48 alerts). Accuracy figures are a comparison
of providers *on this corpus*, not a generalisation to production traffic. The
labels are an independent analyst judgement, **not** reverse-engineered from the
heuristic scorer — which is what keeps the confusion matrix meaningful — but a
larger, real corpus would be needed for statistically strong claims.

## Heuristic triage has known residual errors

The heuristic is a fair, context-aware baseline, not an oracle. It cannot reason
about business context (sanctioned tools, user role, temporal correlation with a
phishing email), so it makes calibration errors — concentrated in the
`benign_suspicious ↔ false_positive` band — that are visible in the confusion
matrix. That is by design: those residual errors are the motivation for, and the
measuring stick of, the LLM layer. The heuristic's conservative profile (it does
not close true positives as false positives) is a deliberate safety bias, and it
too is a modelling choice rather than a universal truth.

## LLM triage caveats

* Requires `ANTHROPIC_API_KEY` and the `anthropic` SDK; otherwise the pipeline
  runs entirely on the heuristic (and says so).
* Cost figures are **approximate** and driven by configurable per-token prices
  (`SOCREPO_PRICE_IN/OUT_PER_MTOK`); they populate the cost table, they are not a
  billing source of truth.
* Model outputs are non-deterministic and can drift as hosted models change; the
  recorded prompt version (`triage-2024.1`) and the confusion matrix are how you
  detect regressions.

## Security scope

Live atomic execution is double-gated (`--live` **and**
`SOCREPO_ALLOW_LIVE_ATOMICS=1`) and Windows-only. The `infra/` stack is a *lab*
topology (single node, demo credentials, no cert rotation) and must only ever be
pointed at disposable VMs you own. It is not a production deployment.
